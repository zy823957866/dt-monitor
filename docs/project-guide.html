一句话理解系统

采集端是浏览器 SDK；控制面是 MySQL 中的项目、Issue、告警与权限元数据； 数据面当前也全部落在 MySQL 事实表；管理端是 Vue 3 + @dt-frames 的后台。 生产目标里的 Redis Stream、ClickHouse、MinIO 还没有接上，所以现在的写入是“同步直写 MySQL”的 MVP 形态。

1 项目定位与边界

SDK
浏览器采集错误、Web Vitals、长任务、埋点、Trace、Replay
API
NestJS 接入公开上报 + 管理查询 + JWT/RBAC + Swagger
UI
Vue 管理端概览、错误、性能、Trace、Replay、埋点、项目、告警

做的是什么

  • 浏览器 RUM：FCP/LCP/CLS/INP/TTFB、FP、长任务、资源错误、JS/Promise/console 异常。
  • 错误聚合：按 fingerprint 归并为 Issue，记录样本堆栈、页面、环境、版本、Trace/Replay 关联。
  • 分布式 Tracing：浏览器 fetch/XHR Span + W3C Trace Context，服务端 OTLP/HTTP JSON 接入。
  • Session Replay：rrweb 兼容录制、采样、gzip 分片上传、MySQL 索引 + 本地分片文件。
  • 管理端：项目/Key/DSN、错误分诊、性能、Trace 瀑布、Replay 时间线、埋点漏斗、告警规则。

明确不做什么

  • 不做全量 DOM 录制、输入值/响应体录制；Replay 只做采样和脱敏。
  • 不做后端全量 APM、Profiling、自动全语言插桩、移动端/小程序 SDK。
  • 不做公网 SaaS 注册、计费、多租户组织隔离。
  • 不替代业务数据库/日志平台；首版不做通用服务端日志收集。
  • 不做完整的漏斗/留存/LTV/归因体系；当前只有基础漏斗接口。
关键术语： DSN 是带项目 ID 和浏览器 public key 的上报地址； Issue 是同一 fingerprint 的错误聚合； Span 是一次调用片段，Trace 是一棵 Span 树； Replay 是 rrweb 事件流的分片，不是视频文件。

4 核心链路：一条事件怎么走

1

SDK 采集与入队

插件生成标准事件，core 补上下文、采样、去重，进入内存队列；默认 50 条/批、5 秒刷一次、上限 1000 条、最多重试 3 次。

packages/sdk-core/src/client.ts
2

浏览器上报

使用 DSN 解析出的 /ingest/v1/:projectId?key=... 发送；页面隐藏/卸载时用 sendBeacon 或 fetch keepalive 尽力送达。

packages/sdk-browser/src/transport.ts
3

公开入口校验

入口标 @Public()，不要求 JWT；校验项目存在、key 类型/状态、事件字段、大小与幂等 eventId。

apps/backend/src/modules/ingest/ingest.controller.ts
4

事务写 MySQL

一个批次在 TypeORM 事务内写埋点/性能/错误/Span；错误按 fingerprint upsert Issue，并递增项目计数。

apps/backend/src/modules/ingest/ingest.service.ts
5

管理端查询

/api/monitor/* 走 Guard → Controller → Service → TypeORM，统一返回 { code: 0, data, message }；前端 http 自动解包。

apps/web/src/api/monitor.ts

当前真实写入路径

浏览器 → Nginx/直连 → NestJS Ingest → MySQL。 没有 Redis Stream、没有消费者组、没有 ClickHouse。接口返回 202 时，数据已经在 MySQL 事务里落库（或整批失败）。 Replay 分片走单独入口，gzip 写入 replay_data，索引写 MySQL。

这适合本地演示和低流量验证，不适合生产高吞吐/可回放/可重试的数据面。

文档里的生产目标路径

浏览器 → 接入层 → Redis Stream → 消费者 → ClickHouse；Replay 分片 → MinIO/S3；MySQL 只保留项目、Issue、告警、权限等控制面元数据。 这条链路目前只存在于 docs/03-architecture.md 和需求文档，代码尚未实现。

阅读时要把“设计目标”和“当前实现”分开，否则很容易误判。

读主链路时优先盯住 6 个文件： packages/contracts/src/types.ts、 packages/sdk-core/src/client.ts、 apps/backend/src/modules/ingest/ingest.service.ts、 apps/backend/src/modules/errors/errors.service.ts、 apps/web/src/api/monitor.ts、 apps/web/src/views/monitor/overview/index.vue。

表用途

monitor_project_keybrowser/server key、状态、轮换历史

monitor_analytics_event埋点事件、属性 JSON、用户/会话/页面
monitor_alert_rule / history告警规则；历史表存在但当前没有写入方

dt_frames（认证库）

用户、角色、菜单、应用注册由外部 auth-server / 权限中心维护，本仓库只读：

  • sys_user / sys_role：用户与角色。
  • sys_menu：菜单与按钮权限码，path 必须与前端静态路由一致。
  • sys_app：OIDC 客户端与回调地址。
  • 本仓库的 seed:monitor-auth 只幂等写入 monitor 应用与 23 条菜单/按钮，不创建用户和普通角色授权。

Redis

在线会话 dt-frame:monitor:online:<jti>、刷新令牌、缓存与全局限流；必须与 auth-server 使用同一实例。

Replay 分片

当前是本地私有目录 REPLAY_STORAGE_DIR（Docker 卷 replay_data），不是对象存储；没有签名 URL、访问审计、孤儿清理。

数据层现状与目标的差距： MySQL 同时承担控制面和事实数据，查询全部走 TypeORM；文档中的 ClickHouse 明细/聚合表、TTL、Redis Stream 消费者、MinIO/S3 对象存储尚未出现在代码和 Compose 中。

10 未实现功能清单（按优先级）

下面的“未实现”指代码里没有闭环，不是指页面没有按钮。P0 是生产数据面/安全闭环，P1 是可用性与工程化，P2 是远期能力。

P0：生产数据面与安全闭环

1. Redis Stream 异步数据面

未实现

当前 ingest.service.ts 在请求线程里开 TypeORM 事务直接写 MySQL。流量上来后，接口延迟、数据库压力和失败重试都不可控；文档要求的 503 语义、消费者组、死信队列也没有。

证据：apps/backend/src/modules/ingest/ingest.service.ts:134 的 dataSource.transaction；仓库没有 Stream/消费者代码。

建议：接入层只做校验和入队，消费者批量写存储；队列不可用时明确返回 503，而不是 202；增加积压/失败指标。

2. ClickHouse 明细/聚合表

未实现

事件、性能、Span 现在都在 MySQL；没有按项目分区、TTL、预聚合和列式查询。管理端 7/30 天聚合会随数据量增长变慢。

证据：apps/backend/src/config/configuration.ts 的 entities 只有 MySQL 实体；docker/docker-compose.yml 没有 ClickHouse。

建议：先建明细表和最小聚合表，消费者批量写入；查询仓库按“事实表/聚合表”分层，保留 MySQL 控制面。

3. Replay 对象存储 + 播放链路

未实现

分片当前写本地目录，没有 MinIO/S3、签名播放地址、访问审计、孤儿分片清理；管理端也没有 rrweb 播放器，只有错误/埋点时间线抽屉。

证据：replay-storage.service.ts 使用 writeFile；replays/index.vue:269 明确提示播放器未接入；replays.controller.ts 没有播放/分片下载接口。

建议：存储抽象接口 + MinIO 实现；增加按 replayId 取分片/签名 URL 的受控接口；前端接 rrweb-player；补访问审计与生命周期。

4. 告警评估与通知

未实现

证据：alerts.service.ts 只有 historyRepo 查询；全仓库没有 @Cron/scheduler；test() 依赖 ALERT_WEBHOOK_URL。

建议：按规则窗口定时聚合错误率/Web Vitals/长任务/可用性；命中后写历史、更新 lastTriggeredAt、按 cooldown 去重；先做 Webhook，再考虑邮件/SSE。
